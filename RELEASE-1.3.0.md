# TRIOZ Business 1.3.0 — обновление от 28.10.2026

Этот документ заменяет инструкции версии 1.2 о парольном входе и отсутствии эквайринга. Старые RELEASE/REPORT сохранены как история. Рабочий сайт на сервере не изменялся: архив содержит исходники, миграции, тесты и инструкции.

## Что изменено

- **Админка:** вместо 11 равноправных кнопок — четыре группы: «Контент», «Клиенты», «Продажи», «Управление». Внутри показывается только выбранный подраздел. Создание услуги и проекта свернуто; услуги объединены в компактный список, уменьшены заголовки и лишние контейнеры.
- **Кабинет:** отдельные разделы «Заказы и оплата», «Счета», «Профиль»; проекты доступны из той же навигации. Понятные пустые состояния, статусы банка и кнопка повторной проверки оплаты.
- **Вход:** только TZ ID для клиентов и администраторов. `/login` и `/enter` перенаправляют в TZ ID-сценарий; POST `/api/auth/login` возвращает 410. Парольные сессии не принимаются. Сброс локального пароля отключён. Локальная роль ADMIN не заменяет актуальное разрешение Business в TZ ID.
- **Медиа:** исправлен 404 для изображений тарифов. Учитываются все ссылки из услуг/проектов/тарифов, а не только первая. Черновые и приватные файлы не становятся публичными. Изображения действительно декодируются, поворачиваются по EXIF и пересохраняются без EXIF; повреждённые и слишком большие по разрешению файлы отклоняются. При недоступном файле отображается аккуратное сообщение, а не значок битой картинки. Файл, используемый другой карточкой, не удаляется.
- **Главная:** уменьшен и сбалансирован заголовок. «Вход» меняется на «Кабинет» для подтвержденной сессии. В футере перечисляются все опубликованные услуги; устаревший `trioz.ru/connect` удалён в том числе из отображаемого текста старых настроек. Основной проект — `https://trioz.ru`.
- **Cookie:** выбор сохраняется и при ещё не опубликованных политиках, но только как необходимые cookie; аналитика остаётся выключенной и пользователь видит причину. При опубликованных документах её можно разрешить. Учтены DNT/GPC. CSRF-токен переиспользуется, чтобы параллельные запросы вкладок не инвалидировали друг друга. Защита от сторонних origin сохранена.
- **Дополнительно:** скрытые тарифы не раскрывают описание через метаданные. Обновлены Nodemailer и Zod, устранены обнаруженные audit уязвимости production-зависимостей.

## Онлайн-оплата Т-Банка

Реализован non-PCI сценарий: создание заказа → серверный `Init` → редирект на банковский `PaymentURL` → подписанное уведомление или серверный `GetState` → статус в кабинете. Данные карты и пароль терминала не попадают в браузер.

- Сумма берётся из сохранённого заказа в целых копейках, не из тела клиентского запроса.
- Оплатить можно фиксированную цену в RUB для предоплаты и одного периода подписки. «По согласованию» и «Без предоплаты» остаются заявками.
- Одностадийная оплата (`PayType=O`), без `Recurrent` и без автосписаний.
- `AUTHORIZED` не считается оплатой; успешная оплата — `CONFIRMED`.
- Проверяются подпись SHA-256, терминал, ID операции и сумма. Дубликаты и запоздалый `AUTHORIZED` не откатывают подтверждённый платёж. Обрабатываются полные/частичные возвраты.
- Повторные и конкурентные нажатия не создают второй активный платёж. После неопределённого результата Init автоматический повтор запрещён: банк мог уже создать операцию.
- Выставление отдельного счёта и карточный checkout блокируют друг друга для одного заказа. Отмена заказа с активным платежом требует сначала урегулировать платёж в банке.
- Платёжная история хранится в новой таблице `BankPayment`. Есть миграции SQLite и PostgreSQL.

**Не реализовано без дополнительного контракта:** автоматическая выдача доступа Premium/другому проекту, продление и рекуррентные списания. Клиент оплачивает один указанный период; доступ выдаётся командой согласно условиям. Возвраты оформляются в кабинете банка, затем синхронизируются уведомлением/проверкой. Локальной кнопки возврата через API нет.

### Серверные переменные

Заполните реальными значениями в защищённом `.env`/секретах сервера, не в исходниках:

```dotenv
NEXT_PUBLIC_APP_URL="https://business.trioz.ru"
TBANK_ENABLED="true"
TBANK_TERMINAL_KEY="<terminal-key>"
TBANK_PASSWORD="<password>"
TBANK_RECEIPT_MODE="bank"
TBANK_TAXATION="<система налогообложения>"
TBANK_TAX="<ставка НДС>"
UPLOADS_DIR="<абсолютный постоянный каталог медиа>"
```

`TBANK_TERMINAL_KEY` и `TBANK_PASSWORD` — серверные значения, **без** префикса NEXT_PUBLIC_. Значения из чата/предположений не подставлены.

**Фискализация обязательна к настройке владельцем:**

- `bank` — передаётся Receipt с email клиента и одной позицией, полной предоплатой и типом товара/услуги. Реализована базовая структура чека ФФД 1.05 для немаркированных товаров/услуг. Согласуйте параметры с вашей онлайн-кассой; при необходимости ФФД 1.2, маркировки, агентской схемы или чека полного расчёта после исполнения нужна отдельная настройка/доработка.
- `external` — приложение не передаёт чек банку. Допустимо только если ваша отдельная касса действительно формирует и отправляет необходимые чеки. Это **не освобождение от 54-ФЗ**; автоматизация внешней кассы в этот архив не входит.
- Ставки/система налогообложения намеренно не выбраны за продавца. При незаполненных обязательных настройках checkout заблокирован.

В админке утвердите продавца и условия, опубликуйте необходимые документы и тарифы. Защитные проверки документов не отключались и шаблоны автоматически не публикуются. Текст оферты и условий должен соответствовать новой схеме оплаты и реальному продавцу.

В терминале банка настройте универсальное подключение и HTTP(S)-уведомления:

```
POST https://business.trioz.ru/api/payments/tbank/notify
```

Этот endpoint должен быть доступен банку по публичному HTTPS без Basic Auth, интерактивной авторизации и CSRF-фильтра прокси. Сам обработчик проверяет банковскую подпись. Ответ при успешной обработке — ровно `OK`.

Проверяйте тестовый терминал на staging с отдельной БД, не смешивая тестовые и боевые заказы. На тестовом терминале проверьте минимум: успех, отказ, прерванный редирект, запоздалое уведомление, повторное нажатие, возврат и поступление чеков. Затем переключайте на боевой терминал. Из sandbox реальное подключение терминала/зачисление денег не проверялось.

### Если Init завершился таймаутом

1. Не сбрасывайте `activeKey` вручную и не создавайте повторный платёж вслепую.
2. Найдите операцию в кабинете Т-Банка по `OrderId`: это `BankPayment.id`, а не `BusinessOrder.id`.
3. Если есть банковский PaymentId, выполните на сервере:

```bash
npm run payment:reconcile -- --payment-id <bank-PaymentId> --attempt-id <BankPayment.id>
```

Скрипт вызывает только GetState и сверяет заказ/сумму/терминал. Нового списания не делает. Если операции нет или её состояние неопределённо, сначала сверка с поддержкой банка. Удалять платёжную историю для повторного списания нельзя.

## TZ ID и существующие аккаунты

Настройте `TZ_ID_CLIENT_ID`, `TZ_ID_CLIENT_SECRET`, `TZ_ID_TOKEN_KEY` и зарегистрированный callback. Назначьте администратору актуальную роль ADMIN именно для клиента Business в центральном TZ ID. Новый пользователь создаётся после проверенного OIDC-входа; административные права проверяются отдельно на сервере.

**До обновления** проверьте, что существующие аккаунты связаны через `TzIdentityLink`. Совпадение email не считается доказательством владения: автоматического объединения нет. Для старого аккаунта без связи оператор должен проверить владельца и получить настоящий `sub` из TZ ID:

```bash
npm run account:link-tz -- --user-id <локальный-User.id> --subject <проверенный-TZ-ID-sub> --confirm-ownership
```

Команда не меняет владельца уже связанного аккаунта и не выдаёт локальную ADMIN-роль; старые сессии завершаются. Это также способ миграции старого администратора без парольного веб-входа. Не указывайте subject по догадке или по одному совпавшему email.

`npm run db:seed` теперь заполняет только начальные услуги/настройки и не создаёт парольного администратора. На обновляемой базе seed не требуется; не используйте старый reset/setup для удаления данных.

## Обновление сервера

1. Сделайте резервную копию PostgreSQL, текущего `.env` и **всего каталога uploads**.
2. Перенесите старые файлы в постоянный `UPLOADS_DIR`; дайте процессу приложения права на чтение/запись. При нескольких репликах каталог должен быть общим. На эфемерном/serverless-диске это файловое хранилище использовать нельзя — потребуется внешнее объектное хранилище.
3. Сохраните SESSION_SECRET и TZ_ID_TOKEN_KEY, настройте TZ ID/терминал/налоги/домен. Не перезаписывайте реальные секреты `.env.example`.
4. В каталоге релиза выполните:

```bash
npm ci
npm run db:generate
npm run db:deploy
npm run lint
npm run typecheck
npm test
npm run build
```

5. Перезапустите ваш процесс приложения (`npm start`/существующий process manager). Не запускайте миграцию `dev` на production.
6. `npm run launch:check` проверяет конфигурацию и БД, включая BankPayment и настройки эквайринга. Это не банковская сертификация, не проверка доставки SMTP и не тест фактической оплаты.
7. Сохраните существующий ежеминутный запуск `npm run jobs:run` для обслуживания очереди писем.

Production — PostgreSQL, как и раньше. Домен business.trioz.ru в конфигурации TZ ID сохранён; ссылка «Основной проект» ведёт на trioz.ru. Если меняется домен самого Business, отдельно обновите контракт регистрации OIDC и проверки конфигурации, а не только ссылку в футере.

## Проверки

Актуальные команды:

```bash
npm test
npm run test:integration
npm run test:admin
npm run test:catalog
npm run test:invoices
```

`test:integration` запускает изолированные сценарии на настоящей временной SQLite-базе с миграциями и имитацией банковских ответов, плюс тесты OIDC callback. Реальные банковские запросы и настоящая оплата этими тестами не выполняются. Старые отдельные scripts/*-check, использующие парольные cookie-fixtures, относятся к версии 1.2; package.json больше их не запускает.

Подробный результат — `TEST-REPORT-1.3.0.md`.
