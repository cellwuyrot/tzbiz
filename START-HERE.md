# TRIOZ Business — обновление 15.10.2026

## Что готово

- Три режима предложения в админке: **без предоплаты**, **с предоплатой**, **подписка**. Одна услуга может иметь несколько предложений. Без предоплаты не означает бесплатно; стоимость можно согласовать позже.
- Premium/VPN — отдельные продукты с настоящим техническим ID TZ ID. Название, описание, отображаемая цена/период и условия редактируются отдельно от этой привязки. Продукты не создаются с выдуманными ID/ценами и не активируются локальными флагами.
- Заявки на конкретный тариф: владелец, снимок цены и условий, версии документов, ключ повторной отправки, защита от устаревшей редакции. История в кабинете и раздел «Продажи и условия» в админке. Статусы заявок не являются банковскими статусами.
- Владелец заполняет реквизиты, контакты и условия на странице оплаты. До их утверждения оформление тарифной заявки закрыто. Это не утверждает автоматически юридические документы и не включает эквайринг.
- Безопасная сериализация JSON-LD; видимый серверный контент без JS; настоящие ссылки на все услуги; публичные медиа разрешены в robots; постоянные редиректы при смене slug; sitemap включает предложения и страницу оплаты; мобильное меню и заметный кабинет.
- Безопасный возврат к предложению после входа, временный черновик в sessionStorage (30 минут при чтении), отказ в доступе при сбое introspection без удаления сессии. Пятиминутная политика TZ ID не ослаблена.
- Общие DB rate limits, идемпотентность публичной формы, транзакционный двухканальный почтовый outbox, фоновые повторы, очистка истёкших сессий и лимитов. Видео: потоковая выдача, Range 206/416 и HEAD.
- Обновлены Next.js, Nodemailer, Vitest и транзитивные зависимости. Полные проверки — в `docs/checks/`.

## Что НЕ готово и почему

**Это не готовый онлайн-магазин и не завершённая интеграция подписок.** В исходном архиве нет действующего контракта биллинга/выдачи Premium/VPN, исходников основной платформы и банковской конфигурации.

Заявки можно согласовывать, но нельзя получить настоящую подписку, подтвердить платёж, списать деньги, отменить банковское продление или вернуть платёж. Препейд-заявки нельзя перевести в исполнение в обход подтверждённой оплаты; подписку нельзя выдать изменением статуса. Для индивидуальных услуг без предоплаты есть рабочие статусы согласования/исполнения/завершения.

Для следующего этапа нужны:
1. Архив/документация основной платформы: реальные ID продуктов Premium/VPN, источник тарифов, создание checkout, состояние подписки, продление, отмена, возврат, выдача и отзыв доступа, аутентификация API, идемпотентные события.
2. Решение, где обрабатывается платёж: центральный биллинг или Business. Нельзя дублировать списания уже работающего биллинга.
3. Sandbox платёжного провайдера и согласованная модель продавца/чеков/договоров. Секреты передавать защищённо, не в чат/README.
4. Утверждённые юридические документы и реальные реквизиты. Текущие документы — draft-4, не юридическое заключение.

До получения этих материалов не включайте обещание автоматической покупки. Отображаемая цена Premium/VPN не меняет стоимость списания в TZ ID; её потребуется сверить с источником истины при подключении адаптера.

## Установка в отдельный staging

Node.js >=22.12.0. Производственный PostgreSQL, тестовый SQLite. Никогда не заменяйте production-базу тестовым файлом.

```bash
npm ci
# Создать .env из .env.example, заполнить реальные настройки (не коммитить).
npm run db:deploy
npm run db:generate
npm run typecheck
npm run lint
npm test
npm run build
npm start
```

Первичная инициализация пустой базы: `npm run db:setup`. На существующей базе используйте `db:deploy`, не `db:setup`: seed переустанавливает пароль администратора из окружения и отзывает его текущие сессии.

Для production задайте `NODE_ENV=production`, PostgreSQL DATABASE_URL, HTTPS NEXT_PUBLIC_APP_URL и случайный SESSION_SECRET не менее 32 символов. TZ ID по текущей политике работает только на `https://business.trioz.ru` с зарегистрированным callback. Миграция PostgreSQL провалидирована по схеме, но не применялась к настоящему серверу.

### Перед миграцией 0007

1. Сделать резервную копию БД и uploads, проверить восстановление и старые миграции 0001–0006.
2. Применить 0007 в staging на копии данных, затем провести приёмку. Миграция добавляет таблицы, не удаляет клиентов, проекты или заявки.
3. Существующие рекуррентные предложения получают режим SUBSCRIPTION, разовые — PREPAYMENT. Старые Premium/VPN становятся черновиками: без достоверного технического ID нельзя публиковать их как готовый центральный продукт. Проверить и переопубликовать вручную после сопоставления с TZ ID. Исторические цены не изменяются.
4. Настроить коммерческие условия в админке. Их `approved=false` по умолчанию; заявки на тарифы остаются закрыты. Публичная форма индивидуальной задачи существует отдельно.
5. Прежние заявки без outbox обслуживаются прежним безопасным ручным retry; новые — очередью. Не переписывать старые согласия на новую версию.

### Обязательный планировщик почты и обслуживания

Новые заявки не ждут SMTP в HTTP-запросе. Они сохраняются вместе с двумя заданиями, которые должен выполнять планировщик:

```cron
* * * * * cd /var/www/tzbiz && /usr/bin/flock -n /tmp/tzbiz-jobs.lock npm run jobs:run >> /var/log/tzbiz-jobs.log 2>&1
```

Используйте фактические абсолютные пути Node/npm в вашем окружении и одного OS-пользователя с доступом к .env. Не запускайте второй независимый планировщик для той же очереди. Публичного cron-эндпоинта нет. Мониторьте код завершения, PENDING/RUNNING/FAILED и задержку очереди.

Обработка SMTP — at-least-once: после аварии на границе принятия SMTP возможно повторное письмо. Это не exactly-once-доставка. После пяти неуспешных попыток задание становится FAILED; администратор может поставить его повторно, подтвердив риск дубля. Успех SMTP не означает попадание в почтовый ящик.

### Reverse proxy

`TRUST_PROXY_HEADERS=false` — безопасный дефолт: внешним IP-заголовкам доверия нет, запросы имеют общий IP-бакет. Для реального трафика включайте true **только** после того, как Nginx/edge перезаписывает x-forwarded-for/x-real-ip и порт приложения недоступен напрямую. Иначе лимиты можно обходить подделкой заголовков. Настройте ограничения размера body, HTTPS и безопасные журналы без кодов/токенов.

### Контрольные проверки

```bash
npm run typecheck
npm run lint
npm test
npm audit --omit=dev
npm run jobs:run
```

`npm run test:integration` предназначен только для локального сервера и одноразовой SQLite-базы с `revision`/`integration` в имени. Он создаёт синтетических пользователей/предложения и не должен запускаться на production. Не задавайте реальные SMTP-настройки для этого теста.

## Остаточные риски

- В полном npm audit остаётся цепочка build/lint-зависимостей через braces 3.0.3: на дату проверки исправленной версии в текущей ветке нет. Это не production/runtime-дерево; не обрабатывайте недоверенные glob-паттерны и не открывайте dev-сервер наружу. Полная миграция Tailwind/линтера — отдельный контролируемый этап, не случайный `audit fix --force`.
- Живые OIDC, SMTP-доставка, PostgreSQL, reverse proxy, эквайринг, Core Web Vitals и фактическая индексация требуют приёмки на сервере. Успешные unit-тесты их не заменяют.
- Сроки хранения заказов/заявок/писем/резервных копий должен утвердить оператор. Очистка истёкших сессий не является полным юридическим регламентом удаления.
- Перед выкладкой обязательно сверить реальные документы. Автоматически придуманных продавца, реквизитов или конечных тарифов в поставке нет.
