## Проверенные границы безопасности

- Для админских API: запрет анонимному пользователю, запрет клиенту, CSRF на изменениях.
- Счёт доступен владельцу и администратору; другому клиенту возвращается 404, анонимному предлагается вход.
- Повторная отправка того же счёта не создаёт дубликат; конфликтующие данные с тем же ключом отклоняются.
- Сверка оплаты требует подтверждения и номера операции. Оплаченный счёт нельзя отменить как неоплаченный; возврат оформляется отдельно у провайдера.
- Параллельное устаревшее изменение отклоняется по редакции.
- Реквизиты продавца сохраняются снимком: последующая смена банка не меняет старый счёт.
- Платёжные ссылки: только HTTPS, точный разрешённый домен, без userinfo и нестандартного порта. Домены тестового провайдера фиктивны и не должны использоваться для реальной оплаты.
- Сверенная оплата не активирует подписку TZ ID. Для предоплатной услуги начало работ требует полной суммы связанных сверенных счетов.
- Клиент с финансовой историей не удаляется; возвращается понятный HTTP 409.
- В диагностике не выводятся исходные ошибки, строки подключения, пароли и токены. Используется безопасная категория и код обращения.

## UI и печать

Проверены девять разделов админки при ширине 1440 и 390 px: Услуги, Проекты, Заявки, Клиенты, Настройки сайта, Интеграции, Тарифы и подписки, Счета, Продажи и условия. Горизонтального переполнения страницы нет; ошибок JavaScript в браузере не обнаружено.

Дополнительно проверены формы трёх способов выставления счетов, раскрытые реквизиты продавца, комментарии и почтовые статусы, ошибки 401/403/503 и восстановление после ошибки. После сбоя не остаётся ложная «Загрузка состояния…». Печатная форма тестового банковского счёта сохранена в PDF: одна страница A4, белый фон и читаемый чёрный текст.

Скриншоты в этой папке содержат только синтетические тестовые записи. Реквизиты на них не предназначены для переводов.

## Что эта проверка НЕ подтверждает

- Работоспособность рабочей PostgreSQL, прокси, HTTPS и прав пользователя БД в окружении владельца.
- Реальный OIDC-вход, доступность внешнего TZ ID, назначения ролей и отзыв доступа на сервере владельца.
- Доставку SMTP в реальные ящики и корректность SPF/DKIM/DMARC.
- Оплату реальными деньгами, актуальные API провайдера, подпись webhook, автоматические повторные списания, отмену или возврат.
- Кассовые чеки и соответствие юридических документов фактической модели бизнеса.
- Нагрузочную устойчивость и полный независимый аудит безопасности.

`npm run launch:check` в изолированной среде ожидаемо завершился с кодом 1, поскольку нет рабочей PostgreSQL, реальных SMTP/TZ ID и юридического утверждения. Успешные локальные тесты не снимают эти блокеры.

**Вывод:** готова техническая поставка портала и ручного выставления счетов. Автоматические эквайринг, рекуррентный биллинг и выдача подписок TZ ID остаются отдельной незавершённой интеграцией. Порядок настройки и ограничения описаны в корневом RELEASE-1.1.0.md.
