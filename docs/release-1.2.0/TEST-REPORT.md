## Проверенные сценарии

### Сохранённые возможности

- Анонимный пользователь, клиент и администратор: 401/403, CSRF-защита мутаций.
- Создание/редактирование/сброс пароля/удаление клиента с учётом финансовой истории.
- CRUD проектов и услуг, загрузка/перестановка/удаление медиа, перенаправление старого slug, защита занятых старых адресов.
- Серверная привязка заявки к опубликованной услуге, идемпотентность, два задания почтовой очереди одной записью; ошибка SMTP не удаляет заявку.
- Поиск и пагинация, длинные комментарии и email не расширяют страницу; последняя заявка клиента не зависит от страницы общего списка.
- Счета на банковский перевод, эквайринг и рекуррентную оплату по внешней ссылке; запрет чужого счёта, ручное доказательство сверки, конфликт версии и терминальные состояния.
- Снимок реквизитов продавца не меняется при редактировании продавца. Работа по предоплате не начинается до полной суммы сверенных связанных счетов.
- Оплаченный внешний подписочный счёт **не выдаёт выдуманное право TZ ID или trioz.ru**.
- Ошибки интеграций 401/403/503 показывают сообщение, загрузка не зависает, затем состояние успешно восстанавливается.
- Белый счёт в печати: PDF A4, 1 страница с тестовыми данными; cookie-элементы скрыты печатным CSS.

### Новый функционал

- Публикация универсальной карточки без обязательной локальной Service, целевой проект, состав, условия предоставления, цена. Внутренняя заметка не попадает в публичную карточку.
- Некорректные адреса проекта, внешние/исполняемые изображения и отсутствие условий предоставления отклоняются.
- Загрузка изображения увеличивает редакцию карточки и создаёт аудит; устаревшая загрузка отклоняется.
- Сохранение черновика не меняет публичную редакцию. Требуются подтверждение владельца и актуальная версия черновика.
- Старые юридические публикации доступны по исходной версии. Текст с `<script>` отображается как текст, а не выполняется.
- Устаревшие версии согласий и отсутствие ознакомления с офертой отклоняются. Без обязательных публикаций сервер закрывает оформление.
- Заказ сохраняет проект, характеристики, цену и версии документов; редактирование карточки не меняет прошлый заказ. Повтор запроса не создаёт дубликат.
- До разрешения аналитики записи в агрегатах нет. После разрешения сохраняются только день, публичный путь и счётчик.
- DNT/GPC, чужой Origin, приватные пути и параметры URL исключаются. Изменение политики отключает старое разрешение. Отзыв прекращает последующий сбор.
- Браузер проверил реальный выбор cookie, переход на другую публичную страницу и прекращение учёта после отказа.
- Исправлен найденный реальным браузерным прогоном дефект: собственное BroadcastChannel-уведомление раньше могло удвоить первый просмотр. Повторный прогон подтвердил один запрос.
- Планировщик удаляет агрегаты старше 180 дней. Админский отчёт ограничивает периоды и не называет просмотры уникальными посетителями.

## Воспроизведение

Базовые проверки:

```bash
npm ci
npm run db:generate
npm run lint
npm run typecheck
npm test
npm run build
```

Для HTTP/DB сценариев нужна **отдельная одноразовая SQLite**, путь которой содержит `integration`, loopback URL, отключённый SMTP и отдельный случайный `SESSION_SECRET`. Настройки URL и ключа должны совпасть в тестовом Next-сервере и процессах проверок. Не запускать на production, не использовать рабочие аккаунты/провайдера. В тестовом окружении `NODE_ENV` не задаётся как production при `db:deploy`/`build`, поскольку production-guard этих скриптов требует PostgreSQL; Next `start` запускается как оптимизированный сервер.

После `db:deploy`, `build` и запуска сервера:

```bash
npm run test:integration
npm run test:invoices
npm run test:admin
npm run test:catalog
```

Передавайте `AUDIT_BASE_URL` и `INTEGRATION_ARTIFACT_DIR`; последний каталог содержит закрытую `qa-fixture.json` с **тестовыми** cookie и не должен публиковаться. Сценарии создают синтетические записи и намеренно публикуют синтетические документы. Они не предназначены для чистки или проверки рабочей БД. Желательно использовать новую базу на каждый полный прогон; многократные прогоны в одном окне закономерно упираются в настоящие rate limits. Сброс лимитов выполнялся только в изолированной тестовой базе перед повторным UI-прогоном, не в приложении и не в production.

Опциональные браузерные сценарии `scripts/ui-check.cjs` и `scripts/print-errors-check.cjs` требуют Playwright и Chromium в отдельной QA-среде. Playwright не добавлен как production-зависимость. Используют те же URL, артефактный каталог и тестовые фикстуры; `CHROMIUM_PATH` позволяет выбрать установленный Chromium. Для сборки из исходников нужен доступ к реестру зависимостей и ресурсам Google Fonts при работе `next/font`; браузер затем получает шрифты с самого сайта.

JSON-результаты и выбранные снимки лежат рядом с этим отчётом. На изображениях и в PDF — только синтетические реквизиты и записи; **не использовать для оплаты**. Тестовые базы, cookie, `.env`, `node_modules`, `.next` в поставку не включены.

## Что не подтверждено

- Реальная PostgreSQL: схема валидирована, но PostgreSQL-сервера в окружении не было. Миграцию и резервное восстановление обязательно прогнать на staging PostgreSQL.
- Вход, роли и проверка подписки на **trioz.ru**: исходников/контракта этого приложения нет. Для Business OIDC есть регрессионные проверки, но реальные credentials и вход пользователя в production не использовались.
- SMTP-доставка в ящики: намеренно не отправлялись реальные письма.
- Банковские платежи, подписи webhook, автосписания, возвраты, чеки и выдача внешних прав: соответствующие API не подключены.
- Юридическая корректность текстов, реальные реквизиты, основания и сроки обработки: требуется владелец и профильная проверка.
- Полная безопасность инфраструктуры, нагрузочная устойчивость, резервирование и мониторинг production: этот локальный прогон их не заменяет.

`launch:check` в изолированной HTTP/SQLite среде **ожидаемо завершился с кодом 1**: нет production PostgreSQL/HTTPS, декларации владельца, реального SMTP/TZ ID и постоянно запущенного расписания. Это не скрыто как «всё готово». Проверка схемы и наличие синтетических документов прошли, но тестовые условия не являются рабочими.
