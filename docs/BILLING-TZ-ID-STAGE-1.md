## Фактическая архитектура до обновления

Next.js 15 App Router / React 19 / TypeScript / Tailwind; Prisma 6, PostgreSQL production и SQLite development. Собственные пользователи ADMIN/CLIENT, bcrypt-пароли, httpOnly-сессии, CSRF для изменений и серверные проверки ролей. Админка управляет услугами, проектами, клиентами, заявками и настройками. Публичная форма сохраняет LeadRequest до независимых попыток отправить два письма существующим Nodemailer. SMTP настраивается на сервере, а не через браузер. Есть публичные юридические документы, версии согласий, независимые почтовые статусы и безопасная диагностика. До этого этапа не было платёжных моделей, подписочного каталога и клиентского подключения TZ ID.

## Реализовано

### Каталог

В админке раздел «Тарифы и подписки»: разовые / рекуррентные предложения, услуга Business либо Premium/VPN, описание, цена RUB, период, условия продления/отмены, внутренняя заметка, черновик/публикация/архив. Автоматических цен и финансовых подписок нет. Черновик допускает отсутствие цены; публикация требует цены и текста отмены. Рекуррентное предложение требует периода и условий продления. Каталог `/plans` показывает только опубликованные неархивные предложения; услуга Business тоже должна быть опубликована. Внутренняя заметка не выдаётся публично. Изменения тарифов сохраняют редакцию и журнал с автором в одной транзакции; конкурентное устаревшее изменение получает HTTP 409. Исторические записи не удаляются через UI.

### TZ ID

Из предоставленного примера подтверждены issuer `https://id.trioz.ru`, OIDC discovery/JWKS, Authorization Code + PKCE S256, `client_secret_basic`, RS256 и `/userinfo`, интроспекция и отзыв. Business подключается стандартным `openid-client`, не копирует центральную БД и не использует email как идентификатор. Связь — уникальная пара `(issuer, sub)`.

`/account` — существующий локальный аккаунт и возможность центрального входа. Новый подтверждённый TZ ID может создать локального CLIENT с контактными данными для совместимости Business; центральный профиль при этом остаётся в TZ ID. Совпадающий email существующего Business-пользователя не связывает аккаунты автоматически. Для явного связывания требуется текущая локальная сессия, CSRF, подтверждение локального пароля и успешный вход в TZ ID. Центральные claims не назначают ADMIN. Существующие локальные пароли и роли сохранены.

Проверяются state/одноразовое поглощение state в БД, nonce, PKCE, issuer, subject, RS256/JWKS-подпись ID token и соответствие `/userinfo`. Access token хранится зашифрованным AES-256-GCM отдельным ключом. Секрет клиента и ключ не выдаются в браузер. Метаданные админки показывают только наличие настроек, не значения секретов.

**Ограничение этапа:** TZ ID-сессия Business не больше 5 минут и сроков токенов; на проверках пользователя выполняется интроспекция. Недоступность/отзыв центрального токена закрывает именно TZ ID-сессию. По истечении требуется новый вход через центральный SSO. Refresh/offline_access не запрашиваются и фоновая синхронизация не реализована. Старая локальная парольная сессия остаётся отдельным механизмом на 7 дней: отзыв TZ ID не отзывает её автоматически. Старые/истёкшие сессии удаляются при обращении; login attempts очищаются при новом входе с запасом по времени, не мгновенно. Политику долговременного хранения ещё должен утвердить оператор.

### SMTP и документы

Почта остаётся на Nodemailer/SMTP; REST API SMTP-сервиса и API TZ ID — разные интеграции. Исправлена классификация отказа `MAIL FROM` (отправитель) отдельно от `RCPT TO` (получатель), неизвестного конверта и таймаута проверки без отправки. Это не подтверждает доставку в ящик.

Юридические документы обновлены до `2026-10-13-draft-3`, точная предыдущая draft-2 сохранена. Добавлены фактический каталог, условный TZ ID-вход, состав идентификаторов/токенов и характер передачи данных. Тексты: `docs/AGREEMENT.md`, `docs/PRIVACY.md`, публичные `/agreement`, `/privacy`. Это по-прежнему предварительные документы, а не утверждённая оферта для эквайринга. Владелец должен подтвердить полное наименование/статус оператора, реквизиты/адрес, основания обработки, сроки хранения и удаления, договоры с получателями данных и SMTP-провайдером, действительные коммерческие условия, отмены/возвраты и отдельное согласие на рекуррентные списания.

## Следующие этапы: настоящие платежи

Целевая схема: TZ ID удостоверяет клиента → Business хранит коммерческий заказ/снимок тарифа/согласие → сервер Business создаёт сессию Т-Банка → проверенный серверный callback подтверждает транзакцию → идемпотентная обработка выдаёт локальную услугу или передаёт подтверждённое событие доверенному API доступа → профиль TZ ID отображает состояние. Редирект браузера не подтверждает оплату. Основной публичный сайт не обязан иметь checkout.

В примере уже есть CloudPayments, PremiumSubscription/VpnSubscription и отдельная модель внешних подписок клиента TZ ID. `PUT /api/v1/subscriptions` — пользовательский Bearer + scope subscriptions:write; запись внешней подписки **не активирует Premium/VPN**. `GET /api/v1/subscriptions`, контактные и notification API существуют, но универсального серверного API выдачи Premium/VPN и client_credentials-публикатора не обнаружено. В этом этапе Business не вызывает эти методы и не меняет основную платформу.

1. Утвердить юридического продавца, платёжные сценарии, товары, тарифы/валюту, налоги/чеки, возвраты, отмены и согласие на рекуррентные списания; проверить договор с Т-Банком и актуальную серверную документацию/возможности терминала.
2. Подтвердить sandbox/prod TerminalKey и пароль через защищённый ввод, параметры уведомлений, чеков и рекуррентного механизма. Не сохранять карточные реквизиты в Business; не включать фиктивный checkout.
3. Отдельно согласовать с владельцем TZ ID механизм выдачи/продления/отзыва Premium/VPN по `(issuer, sub)`, scoped S2S, идемпотентные external IDs, возможные статусы и сроки, авторизацию/аудит. Если основной проект нельзя менять, эта часть остаётся блокером; email или прямой доступ в его production БД не заменяют контракт.
4. В Business добавить согласованную модель Order/Payment/Subscription/PaymentEvent/Consent/Outbox и миграции обеих БД. Точный дизайн после банковского и fulfillment-контрактов. Цена/условия фиксируются при покупке, не берутся из редактируемого тарифа задним числом.
5. Планируемые новые файлы (ещё не существуют): `lib/payments/tbank.ts`, `lib/billing/orders.ts`, `subscriptions.ts`, `fulfillment.ts`; маршруты `/api/billing/checkout`, `/api/billing/subscriptions/[id]/cancel`, `/api/payments/tbank/notification`. Проверять подпись/сумму/валюту/заказ/состояние на сервере; уникальные события и атомарные переходы исключают повторную выдачу.
6. Рекуррентность: отдельное согласие/версия/время, первая подтверждённая банковская привязка, серверное расписание, запрет дублей списания, отмена до нового списания, обработка неизвестного результата через сверку, а не слепой retry. Минимальный DB-outbox/worker потребуется обосновать для гарантированной выдачи; тяжёлая внешняя очередь не добавляется автоматически.
7. Изолированные sandbox-тесты оплаты/повторов/webhook/отказов/возвратов/отмен/истечения/доступа, затем только согласованный rollout. Существующий CloudPayments основного проекта не переносить/не отключать автоматически, его рекуррентные привязки не считать переносимыми.

## Блокеры и границы проверки

Нужны регистрация Business как клиента существующего TZ ID и его секрет; разрешённые redirect/scopes; юридическое утверждение новых данных и текстов; банковская конфигурация/сценарии/документация; утверждённые цены и fulfillment API Premium/VPN. Наличие OIDC-клиента в коде не доказывает доступность issuer на production. Реальная SMTP-доставка требует отдельной проверки SMTP-сервиса/relay/DNS/ящиков.

Проверки данного этапа и развёртывание описаны ниже в отчёте результатов и `DEPLOY-BILLING-TZ-ID-STAGE-1.md`. Успех unit-тестов не означает проведённый банковский тест, проверку производственного PostgreSQL или живой OIDC handshake.
