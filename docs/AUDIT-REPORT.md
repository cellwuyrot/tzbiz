# TRIOZ Business — аудит и точечная доработка

Дата: 13 октября 2026. Источник: предоставленный архив tzbiz-main.zip. Работа выполнена только в локальной копии; production, Nginx, PM2, другие проекты, реальная база и реальные SMTP не изменялись.

## 1. Итог и статус
Реализованы независимые клиентское и внутреннее уведомления через существующий Nodemailer, два явных обязательных согласия, версии/время принятия, публичные страницы соглашения и политики, ссылки/SEO и дополнительные тесты. Архитектура, роли, сессии, проекты, админка и каталоги сохранены; проект не переписан. Доработанный архив — исходники, не автоматически развёрнутый сервис.

Документы являются полной **предварительной редакцией**, а не юридически утверждённым комплектом: нет подтверждённых реквизитов оператора, сроков хранения и ряда оснований/получателей. Они помечены соответствующим предупреждением на публичных страницах. Полные тексты приложены ниже и находятся в docs/AGREEMENT.md / docs/PRIVACY.md; серверная версия совпадает с текстами страниц.

Реального API основной платформы не обнаружено, её исходники не предоставлены. Оплата и подписки не имитировались; подготовлен только явно предложенный контракт/план для согласования. Найдены также риски в зависимостях: npm audit не прошёл, требуется отдельный этап исправления до выпуска.

## 2. Фактическая архитектура до изменений
- Next.js App Router / React / TypeScript / Tailwind. Установленные lockfile-версии при проверках: Next.js 15.5.26, Prisma 6.19.3, Vitest 3.2.7. package.json объявляет диапазоны, не эти точные версии.
- PostgreSQL для production и SQLite локально. `scripts/prisma-sync.mjs` выбирает provider по DATABASE_URL, копирует provider-схему и историю в generated schema.prisma/migrations. NODE_ENV=production требует PostgreSQL. Порядок исходных миграций: 0001_init → 0002_content → 0003_leads.
- User/Session — локальные аккаунты и сессии; ADMIN/CLIENT; Project — назначенные клиентам проекты; Service/ServiceMedia/SiteSettings — контент; LeadRequest — заявки. Подписок, платёжных моделей и provider webhook нет.
- Вход: Zod, bcrypt, double-submit CSRF и in-memory лимит попыток. Сессия хранится в БД как HMAC-хеш случайного cookie-токена; HttpOnly, SameSite=Lax, Secure production, 7 дней. Каждая защищённая страница и API проверяет роль на сервере; middleware только устанавливает noindex.
- Admin CRUD клиентов, сброс паролей с отзывом сессий, проекты, услуги/медиа/настройки, просмотр/статусы/удаление заявок. Клиентский кабинет получает только назначенные проекты. Загрузка медиа контролирует MIME/расширение/размер и сигнатуру изображения; выдача проверяет публикацию или доступ пользователя.
- Исходная последовательность заявки: проверка Origin → лимит 4/15 минут → JSON/Zod/honeypot → поиск опубликованной услуги → сохранение LeadRequest/privacyConsentAt → одно внутреннее SMTP-письмо → 201 {ok,emailNotified}. Ошибка SMTP не удаляла запись, но целиком логировалась; письмо клиенту отсутствовало. Форма не учитывала emailNotified.
- `trioz.ru/connect?service=<slug>` — внешняя ссылка, не серверная интеграция. Совпадение локального email/заявки в админке не связывает идентичность с платформой.

Первичный список рисков до реализации: docs/AUDIT-INITIAL.md.

## 3. Существенные изменения и файлы

### Почта и заявка
- `lib/mailer.ts`: сохранён существующий Nodemailer; один transport, два независимых сообщения через Promise.allSettled. Клиенту — благодарность, номер, услуга, следующие шаги и контакт без вымышленных сроков. Команде — ID/UTC-время, имя/email/телефон/компания, услуга/slug и сообщение, Reply-To клиента. Два разных текстовых/HTML-шаблона, динамические строки экранируются, переносы сохраняются. Клиент не получает внутреннее описание задачи/контакты из внутреннего шаблона. Успех означает принятие SMTP, не попадание в inbox. Ошибки журналируются только фиксированной категорией.
- `app/api/leads/route.ts`: сначала сохранение, затем почта; generic JSON 500 при ошибке persistence, без исходной ошибки. Сохраняются обе даты и серверные версии. Публичный успешный формат `201 {ok:true,emailNotified:boolean}` оставлен; true теперь требует успеха обоих каналов. Неожиданное исключение mailer даёт false, не откатывает заявку.
- `.env.example`: SMTP_HOST/PORT/SECURE/USER/PASS, EMAIL_FROM=union@business.trioz.ru, LEADS_EMAIL_TO=info@trioz.ru, отдельный EMAIL_REPLY_TO=info@trioz.ru. Только примеры/placeholder, не действительные реквизиты. Явное SMTP_SECURE=false уважается; без implicit TLS требуется STARTTLS. SMTP_USER не обязан совпадать с sender.
- `README.md`: актуальная почтовая логика, значения и ограничения доставки, обязательные согласия, двухпровайдерные миграции, URL Business, release-gates и ссылки на отчёты. Старые утверждения о необходимости логина info@trioz.ru заменены корректным контрактом.

Проверены доступные файлы схем/кода, README, исходные REPORT-файлы, seed-контент и env.example. Подтверждённые полное наименование оператора, ИНН/ОГРН/адрес и утверждённый retention не установлены. 5. Реальные production HTTPS, proxy headers, доступ к БД, логирование, backup, восстановление и incident-response. Политика отражает код, не сертифицирует сервер.
6. Адрес Business/canonical, отсутствие неизвестных callers старого API, согласованные business-сроки коммуникации (если они появятся), архивирование версий документов и порядок информирования об изменениях.

## 6. Подписки, API и платежи
Основная платформа не доступна как исходники/API. Единственная фактическая связь — внешняя ссылка connect с выбранной услугой. Нет оснований придумывать имена таблиц, токенов, тарифов, статусов или маршрутов.

Предлагаемая схема: подтверждённый вход/связывание по стабильному subject → server-to-server чтение платформенного статуса/entitlements → server-side checkout основной платформы → provider webhook, проверяемый и идемпотентно обработанный на доверенном сервере платформы → Business читает авторитетный результат. Email не единственное доказательство принадлежности; редирект не подтверждение оплаты. Дубликаты/устаревшие события не выдают повторный доступ. Отмена, отказ, возврат и истечение определяются правилами и состоянием платформы.

Подробный предложенный контракт, критерии и условные конкретные файлы Business — docs/INTEGRATION-PLAN.md. Это проект для согласования, не контракт на основании обнаруженного API. Подписки не копируются независимо и прямой обход API к production-БД не добавлен.

Нужно установить сценарий: оплата услуги Business, покупка тарифа платформы или продление. Затем получить API/авторизацию/test environment, провайдера/серверную документацию/webhook/sandbox, утверждённые тарифы/цены/валюты, порядок платежей/отмен/возвратов/учёта и юридические данные.

## 7. Оставшиеся технические риски и минимальный retry-план
- Заявка сохранена, но SMTP-попытки best-effort. Остановка процесса после commit или timeout после SMTP acceptance может оставить отсутствие уведомления либо неоднозначную доставку. Durable retries не реализованы и не обещаются.
- Если гарантированные попытки нужны, минимальное совместимое решение: таблица outbox в обеих схемах, запись двух channel-job в транзакции с LeadRequest, ограниченные попытки/backoff/nextAttemptAt, блокировка конкурирующих workers и административный контроль dead-letter. Уникальность lead/channel/documentVersion не даёт SMTP exactly-once; надо учитывать дубли при неоднозначном таймауте. Содержимое писем не логировать, retention очереди утвердить. Тяжёлая внешняя очередь без необходимости не предлагается.
- In-memory rate limit не распределён и доверяет forwarding-заголовкам; expired ключи сами не удаляются. Существующую Nginx/proxy-конфигурацию не меняли. Нужна отдельная проверка real proxy и антиспама до масштабирования.
- Публичный lead endpoint допускает отсутствующий Origin; его защита — Origin-check при наличии, honeypot/Zod/лимит, а не CSRF-token. Авторизованные изменяющие маршруты сохранили double-submit CSRF.
- В существующих admin leads catch-all ошибки БД могут превращаться в 404/ложный успех удаления; в создании проекта ранний отказ после сохранения превью может оставить orphan-файл. Эти исходные ошибки зафиксированы, но CRUD не менялся вне согласованного объёма. Нужны отдельные узкие исправления и тесты.
- Не проверены все возможности production, сторонние scripts инфраструктуры, длительные нагрузочные сценарии и миграция на действительной PostgreSQL.

## 8. Блокеры и порядок выпуска
Блокеры: подтверждённые SMTP host/port/secure/login/secret и разрешённый union sender; реальная отправка на согласованные тестовые адреса; оператор/правовые основания/retention/получатели/регламент; основная API-спецификация/identity/payment scenario/provider/prices; dependency remediation и PostgreSQL staging.

Рекомендуемый порядок: юридическое и SMTP-согласование → отдельное исправление зависимостей с regression-suite → staging PostgreSQL с backup/полной историей 0001→0004 и Prisma generate → lint/typecheck/test/build → реальная тестовая отправка/отказы → согласованный production migration/release. Production команды в исходном README не выполнялись. Не повторять всю заявку для повторной отправки писем.

Поставка исключает node_modules, .next, локальные БД, runtime uploads, .env/секреты и .git. Исходный функционал и старые canonical provider-миграции сохранены.

# Пользовательское соглашение

Редакция: 2026-10-13-draft-1

Предварительная редакция для согласования владельцем. Юридическое наименование и реквизиты оператора, основания обработки и сроки хранения требуют подтверждения до окончательного утверждения. Обозначение TRIOZ Business является названием проекта, а не подтверждённым наименованием юридического лица.

## 1. Общие положения

TRIOZ Business — сайт с информацией об IT-услугах, публичных проектах и формой обращения. Пользователь — посетитель сайта или обладатель предоставленной учётной записи. Оператор — лицо, ответственное за работу сайта; его полное наименование и реквизиты подлежат подтверждению владельцем проекта.

Соглашение описывает использование возможностей сайта. Пользователь знакомится с этой редакцией до отправки формы и отдельно отмечает её принятие. Обработка персональных данных описана в отдельной политике и сопровождается отдельным согласием.

## 2. Услуги и возможности сайта

На сайте можно ознакомиться с опубликованными услугами, описаниями этапов и состава работ, медиа и публичным портфолио, выбрать услугу и направить описание задачи. Содержание каталога управляется командой TRIOZ.

Описание услуги не устанавливает индивидуальную цену, срок выполнения или гарантию результата. Объём работ и условия сотрудничества обсуждаются отдельно. Ссылка на trioz.ru/connect ведёт на основную платформу; наличие ссылки не означает единую авторизацию, общую подписку или подключённую оплату.

## 3. Отправка и обработка заявок

Для отправки заявки необходимы имя, email, телефон, выбранная услуга, описание задачи, принятие соглашения и согласие на обработку данных. Компания указывается по желанию. Пользователь сообщает корректные контакты и не включает в свободный текст пароли, платёжные данные и избыточные сведения о себе или других лицах.

Сервер проверяет данные и доступность услуги, затем сохраняет заявку. После сохранения система предпринимает независимые попытки отправить подтверждение на email пользователя и уведомление команде. Сбой почтового сервиса не удаляет сохранённую заявку; успешное сохранение не гарантирует доставку письма.

Подача заявки сама по себе не является оплатой, оплаченной услугой или автоматическим заключением договора. Команда рассматривает обращение и связывается по указанным контактам для обсуждения дальнейших шагов. Определённый срок ответа этим соглашением не устанавливается.

## 4. Учётные записи и клиентский кабинет

Учётные записи клиентов предоставляются администратором. Самостоятельная регистрация через форму заявки не предусмотрена. Кабинет показывает проекты, назначенные локальному аккаунту; администратор управляет клиентами, проектами, услугами и заявками.

Пользователь сохраняет конфиденциальность данных входа, не передаёт их посторонним и сообщает команде о подозрении на компрометацию. Администратор может сбросить пароль клиента с отзывом действующих сессий. Аккаунт TRIOZ Business не считается автоматически аккаунтом основной платформы по совпадению email.

## 5. Права и обязанности

Пользователь вправе знакомиться с публичной информацией, направлять обращения и использовать предоставленный доступ по назначению. Не допускаются попытки получить чужие данные, обойти ограничения доступа, отправлять спам или вмешиваться в работу сервиса.

Оператор обеспечивает разграничение доступа к предусмотренным функциям, рассматривает обращения и может обновлять содержание сайта и применять технические ограничения для защиты. Пользователь обязан предоставлять сведения, которыми он вправе распоряжаться, и не нарушать права других лиц.

## 6. Интеллектуальная собственность и материалы

Тексты, дизайн, программные компоненты и опубликованные материалы могут охраняться интеллектуальными правами. Просмотр сайта не передаёт исключительных прав или лицензии на использование материалов вне предусмотренных возможностей сайта. Для такого использования необходимо соответствующее разрешение правообладателя.

Направляя описание задачи и материалы, пользователь подтверждает, что вправе передать их для рассмотрения обращения. Передача заявки не означает передачу исключительных прав на её содержимое или автоматическое разрешение на публичную публикацию персональных данных.

## 7. Доступность и сторонние системы

Доступность сайта зависит от сети, инфраструктуры, базы данных и стороннего почтового сервиса. Возможны технические перерывы, ошибки и ограничения частоты запросов. Непрерывная работа и доставка всех сообщений не гарантируются этим документом.

При переходе по внешней ссылке пользователь обращается к отдельному ресурсу. Его возможности и условия следует проверять на соответствующей платформе. Сайт TRIOZ Business в этой редакции не реализует оплату или предоставление подписки на основании клиентского редиректа.

## 8. Коммуникация и изменение условий

Для обсуждения заявки используются указанные пользователем email и телефон. Технический адрес отправки подтверждения — union@business.trioz.ru при разрешении SMTP-провайдера. Контакт команды: info@trioz.ru. Маркетинговая рассылка не входит в согласие по обычной заявке.

Актуальная редакция публикуется на странице /agreement с обозначением версии. Новые заявки фиксируют время принятия и версии документов на сервере; изменение текста не подменяет сведения о ранее принятой редакции. Для вопросов по работе сайта и документам можно обратиться на info@trioz.ru.

# Политика обработки персональных данных

Редакция: 2026-10-13-draft-1

Предварительная редакция для согласования владельцем. Юридическое наименование и реквизиты оператора, основания обработки и сроки хранения требуют подтверждения до окончательного утверждения. Обозначение TRIOZ Business является названием проекта, а не подтверждённым наименованием юридического лица.

## 1. Назначение политики и оператор

Политика описывает фактическую обработку в TRIOZ Business: рассмотрение обращений, связь с заявителем, предоставление локального клиентского доступа и защиту сайта. Контакт по данным — info@trioz.ru. Юридическое наименование, адрес и реквизиты оператора пока не подтверждены; эта редакция требует утверждения владельцем.

## 2. Цели и основания обработки

Данные заявки используются для её рассмотрения, уточнения задачи, связи с пользователем и отправки подтверждения. Согласие на эту обработку оформляется отдельным обязательным чекбоксом до отправки формы. Оно не включает маркетинговую рассылку и не означает оплату или заключение договора.

Учётные данные и сессии используются для входа, разграничения доступа и предоставления назначенных клиенту проектов. Технические ограничения запросов служат защите от злоупотреблений. Правовые основания для учётных записей, защиты, возможных обязательных записей и иных процессов должен подтвердить оператор до утверждения политики; отдельный чекбокс заявки не подменяет основания всех этих процессов.

## 3. Состав данных

Форма собирает имя, email, телефон, необязательное название компании и сообщение. В LeadRequest также сохраняются идентификатор заявки, ссылка на услугу и её название, статус, даты создания и изменения, время согласия на обработку данных, время принятия соглашения и версии документов. Время фиксируется сервером, не по данным браузера.

Для локальных аккаунтов User сохраняет имя, email, хеш пароля, роль и дату создания; Session — хеш идентификатора сессии, идентификатор пользователя и срок действия. Проекты связаны с локальным клиентом. Данные формы не создают аккаунт автоматически. Сопоставление последней заявки по email в админке не подтверждает принадлежность аккаунта основной платформы.

Сервер читает Origin и IP из заголовков прокси для проверки источника и ограничений. В памяти процесса для заявок хранится SHA-256 ключ IP со счётчиком и временем окна; в ограничении входа — ключ IP/email. Эти данные не записываются текущим кодом в LeadRequest. Cookie trioz_session поддерживает вход, trioz_csrf — защиту изменяющих запросов. Сессия рассчитана на 7 дней, CSRF-cookie — на 1 час. Правила и сроки журналов хостинга и прокси по архиву установить нельзя.

Поле website является антиспам-ловушкой; непустое значение отклоняется, оно не сохраняется в заявке. Аналитические или маркетинговые трекеры в исследованном коде не обнаружены. Подтверждать отсутствие иных данных в реальной инфраструктуре без её аудита нельзя.

## 4. Операции и получатели

Операции включают получение и проверку данных, запись и хранение в базе, чтение уполномоченным администратором, изменение статуса, использование для связи, передачу при отправке писем и удаление заявки администратором.

Через существующий SMTP-провайдер отправляются два отдельных письма. Подтверждение заявителю содержит его имя, номер заявки и услугу. Внутреннее уведомление на info@trioz.ru содержит контакты, компанию, описание задачи, идентификатор и время создания; Reply-To содержит email заявителя. SMTP-провайдер и почтовые системы получателей участвуют в обработке — данные не остаются исключительно внутри базы сайта.

Конкретные SMTP- и инфраструктурные поставщики, расположение обработки и условия передачи, включая возможную трансграничную передачу, не установлены из архива и требуют подтверждения владельцем. Прямой обмен клиентской базой или подписками с основной платформой в текущем коде не реализован. Переход по ссылке trioz.ru/connect не переносит данные формы; в ссылке может передаваться slug услуги.

## 5. Хранение, удаление и отзыв согласия

Утверждённые сроки хранения заявки, аккаунта, связанных проектов, писем, журналов и резервных копий в архиве не указаны. Автоматический срок удаления заявок кодом не установлен. Администратор может удалить заявку через защищённый интерфейс; это само по себе не удаляет почтовые сообщения, журналы или резервные копии.

Чтобы запросить доступ к своим данным, исправление, прекращение обработки, удаление или отозвать согласие, направьте обращение на info@trioz.ru с достаточными сведениями для поиска заявки. Не отправляйте пароль или платёжные данные. Команда должна проверить принадлежность обращения заявителю перед раскрытием данных; удаление и дальнейшее хранение определяются применимыми основаниями, которые оператор обязан уточнить. Срок ответа и полный регламент удаления этой предварительной редакцией не утверждены.

## 6. Меры защиты и ограничения

В приложении предусмотрены серверная валидация, разграничение ролей и клиентских проектов, хеширование паролей, серверные сессии и CSRF-защита изменяющих авторизованных запросов. Публичная форма дополнительно проверяет Origin, антиспам-поле и частоту запросов. Эти меры не исключают всех рисков и не заменяют защиту инфраструктуры.

Отправка почты требует TLS; в коде уведомлений ошибки не выводятся вместе с содержимым письма, контактами или SMTP-секретами. HTTPS, доступ к базе, резервные копии, обработка инцидентов и журналы production требуют отдельного подтверждения владельцем. Пользователь сохраняет данные входа в тайне и сообщает о подозрении на утечку на info@trioz.ru.

Актуальный текст доступен открыто на /privacy. Для новой заявки сохраняются версия этой политики и время согласия. При изменении документа его версия должна обновляться; ранее записанные сведения не подменяются новым согласием. Контакт команды и обращений по персональным данным — info@trioz.ru.
