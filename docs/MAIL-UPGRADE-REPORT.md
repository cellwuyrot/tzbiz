# TRIOZ Business — реализация обновления почты и админки

Дата: 2026-10-13. Основа: GitHub cellwuyrot/tzbiz, cb7c056f1e076ad1d080eff9913b503d2140b9f9. Изменения подготовлены локально, не отправлены на GitHub и не установлены на production. Сервер пользователя, его PostgreSQL/PM2/Nginx и основная платформа не изменялись.

## 1. Фактическая архитектура до обновления

Next.js App Router + React/TypeScript, Tailwind; серверные API, Prisma, локальные User/Session/Project/Service/SiteSettings/LeadRequest. PostgreSQL предназначен для production, SQLite — для разработки; sync-скрипт выбирает каноническую provider-схему и историю миграций. На сервере пользователя уже успешно применены 0001–0004 и выполнен первичный seed (по предоставленному выводу).

ADMIN/CLIENT разделены; admin API проверяют роль, изменяющие запросы защищены CSRF. Сессии — httpOnly cookie и серверная таблица, пароли — bcrypt. Клиентские проекты привязаны к локальному аккаунту. Эти механизмы не заменены.

Публичная заявка проверяется на Origin/частоту/honeypot, валидируется сервером, выбирается опубликованная услуга, сохраняются заявка и два согласия. Затем существующий Nodemailer отправляет два разных письма независимо. SMTP задаётся переменными окружения. До обновления нет admin-диагностики, устойчивой истории двух каналов и ручного повтора. Основные CTA открывали внешнюю платформу в обход локальной формы.

В репозитории нет подтверждённого API основной платформы, SSO/связей аккаунтов/подписок/checkout/webhook. Доступ к исходникам основной платформы и её API не предоставлен. Письма на info@trioz.ru и ссылки /connect не являются такой интеграцией.

## 2. Реализовано

### Раздел Интеграции

- Новый раздел админки показывает заполненность SMTP host/login/password без их значений, порт/TLS, EMAIL_FROM/LEADS_EMAIL_TO/EMAIL_REPLY_TO, недостающие/некорректные параметры.
- Настройки берутся из **эффективного окружения текущего процесса**, а не из редактируемой в браузере .env. Секреты не возвращаются в API; редактирования паролей/ключей через админку нет.
- Проверка SMTP verify не отправляет письмо. Успех означает соединение/авторизацию, не разрешение sender и не доставку.
- Явный тест с подтверждением отправляет два отдельных диагностических письма на согласованный адрес и внутренний email. Заявка не создаётся. Последний безопасный результат каждой проверки хранится в IntegrationCheck: только тип, время, статус, категория ошибки; получатель и письмо там не хранятся.
- Все новые admin API требуют ADMIN; POST также CSRF. Ограничение: до 3 действий каждого типа за 10 минут на администратора в процессе.
- Блок trioz.ru честно показывает «не подключена», без вымышленного API-ключа.

### Состояния писем и ручной повтор

Два независимых канала, каждый с состоянием, количеством попыток, временем и безопасной категорией ошибки:

| Состояние | Значение |
|---|---|
| UNTRACKED | Нет достоверной истории; у старых заявок попыток 0. Не означает «точно не отправлено» |
| PENDING | Попытка запущена; сохранена перед обращением к SMTP |
| SMTP_ACCEPTED | SMTP подтвердил приём; inbox/отсутствие спама не доказаны |
| FAILED | Настройки/авторизация/получатель/известная ошибка не позволили подтвердить отправку |
| UNKNOWN | Таймаут/неизвестный результат или прерывание; письмо могло быть принято |

Сначала сохраняется заявка; затем отправки выполняются независимо. Результат каждого канала записывается отдельно. Ошибка записи статуса не блокирует второй канал. Публичный контракт 201 {ok:true,emailNotified:boolean} не изменён; внутренние SMTP-ошибки не возвращаются клиенту.

Ручной повтор отправляет только выбранный шаблон через существующий Nodemailer, не создаёт новую заявку, не меняет согласия и не отправляет уже принятый канал повторно. Требует подтверждения риска дубля. Атомарный захват в транзакции защищает от двух одновременных повторов; SMTP вызывается **вне** DB-транзакции. Счётчик попыток и compare-and-set не дают позднему ответу старой попытки перезаписать новую. Задержка повтора 60 секунд; pending старше 2 минут отображается как неизвестный и допускает подтверждённый повтор. Часы UI обновляются каждые 15 секунд; сервер всё равно проверяет актуальное состояние.

SMTP не обеспечивает exactly-once. Тяжёлая очередь не добавлена. Это наблюдаемость + ручной повтор, **не durable outbox и не гарантия автоматической доставки**. После сбоя процесса повтор выполняет администратор; перед UNKNOWN/UNTRACKED нужно проверить ящики. Если бизнесу нужны гарантированные фоновые повторы, следующий отдельно согласованный шаг — transactional outbox двух каналов в обеих БД, с worker, backoff и защитой от дублей.

### Воронка и документы

Основные CTA (шапка, hero, карточка/модальное окно/страница услуги) ведут в #contact этого проекта. Параметр requestService выбирает услугу, параметр service остаётся для каталожного модального окна. Переход из модального окна сохраняет имя, описание и согласия; прямой URL/новая вкладка также работают. Явные внешние ссылки основной платформы сохранены.

## 5. Основная платформа и платежи

Связь после выпуска: посетитель → локальная форма → PostgreSQL tzbiz_business → два SMTP-письма (клиенту и info@trioz.ru) → обработка командой. API основной платформы в этот поток не встроен и не нужен для простой почты.

Для аккаунтов/подписок: подтверждённая авторизация обеих сторон → стабильный subject платформы → минимальная связь аккаунтов → доверенный server-to-server API статуса/прав → Business показывает авторитетный результат. Email не является доказательством связи. Подписки остаются источником истины trioz.ru, напрямую в её production-БД Business не подключается.

Для оплаты: сначала выбрать разовую услугу Business/новый тариф платформы/продление; согласовать тарифы/цены/валюты/возвраты и юридические данные. Сервер основной платформы создаёт checkout через её существующего провайдера; проверенный идемпотентный webhook учитывает платёж; Business читает результат API. Клиентский redirect не выдаёт доступ. Реальные имена endpoint/токенов/таблиц не придуманы. Условные файлы/маршруты следующего этапа и критерии безопасности — docs/INTEGRATION-PLAN.md.

## 6. Блокеры и подтверждения владельца

1. Публикация patch в GitHub, staging с PostgreSQL и согласованное окно выпуска. До этого сервер продолжает работать на прежнем коде.
2. Реальные SMTP_HOST/PORT/SECURE/USER/PASS, право отправки union@business.trioz.ru; тестовые адреса, проверка обоих ящиков/Reply-To и DNS-аутентификации. Секреты вводятся только на сервере, не в Git/чат.
3. Исходники/официальный API trioz.ru, авторизация между сервисами, стабильный ID, API подписок/прав и тестовый контур.
4. Сценарий оплаты, существующий провайдер, серверная документация, утверждённые цены/валюты, учёт/возвраты/отмены. Оплата пока не реализована.
5. Юридическое наименование/реквизиты и адрес оператора, утверждённые основания обработки/отдельный текст согласия, действительные получатели/SMTP-провайдер, размещение/возможная трансграничная передача, сроки хранения по категориям, процедура удаления включая письма/резервные копии, ответственный контакт. Неизвестные сроки и реквизиты не заполнены вымышленными значениями; обе страницы остаются предварительными.
6. Отдельная работа по известным уязвимостям зависимостей.

Сама эта реализация не создаёт общую клиентскую базу или оплату, не подтверждает юридическую готовность документов и реальную доставку почты. Следующие практические шаги описаны в docs/DEPLOY-MAIL-UPGRADE.md.
