# Основная платформа, подписки и платежи

## Факты и границы
В архиве только TRIOZ Business. Исходного кода trioz.ru, спецификации API, конфигурации платёжного провайдера и моделей подписок нет. В рабочем каталоге другой код основной платформы не предоставлен. Производственные БД, секреты и персональные данные не читались, перебор внешних endpoint не выполнялся.

В исходной версии `lib/orders.ts` формировал URL, карточки и footer открывали `https://trioz.ru/connect?service=<slug>`. В доработке наблюдаемости почты основные CTA переведены на локальную форму (`lib/request-service.ts`, `components/request-service-link.tsx`); явные внешние ссылки в footer и разделе Интеграции сохранены. Это смена пути заявки, а не API-интеграция. Нет обмена токенами, SSO, server-to-server запроса, checkout или webhook. User/Session локальны. Последняя заявка в админке сопоставляется по email для удобства, не для доверенного связывания с платформой. Обнаруженного API, на котором можно построить готовую интеграцию, нет.

## Предлагаемый контракт для согласования (НЕ обнаруженный API)
Имена реальных маршрутов, полей, идентификаторов и статусов устанавливает владелец основной платформы. Следующая таблица задаёт семантику, а не утверждает их наличие.

| Операция | Что должен предоставлять согласованный API | Критерий безопасности |
|---|---|---|
| Идентификация | Проверяемый стабильный subject платформы, издатель, назначение и срок полномочий | Поддерживаемый платформой OIDC/OAuth authorization code + PKCE либо документированный одноразовый обмен; проверка state, issuer/audience/expiry, серверное хранение секретов |
| Связь аккаунтов | Подтверждение пользователя с авторизацией в обеих системах | Нельзя использовать один email как доказательство; уникальная пара localUserId/platformSubject, явное подтверждение связывания/отвязки, re-auth и аудит |
| Подписка | Авторитетный статус, начало/истечение и время снимка для конкретного subject | Основная платформа — источник истины; business не вычисляет доступ из локальной оплаты |
| Возможности | Разрешения/entitlements и доступные этому пользователю тарифы | Серверная проверка полномочий; UI не источник доступа; неизвестный/недоступный статус не даёт новые права |
| Checkout | Создание сессии доверенным сервером по согласованному сценарию и тарифу | Сумма/валюта/владелец назначаются сервером; idempotency key; allowlist return URL; клиент не задаёт цену |
| Подтверждение | Проверяемое серверное событие либо server-to-server проверка статуса | Подпись raw body/срок/replay или иной документированный механизм; секреты только на сервере; не редирект и не параметр paid |
| Повтор события | Стабильный идентификатор и версия/порядок события | Уникальный eventId, транзакционная обработка, повтор подтверждается без повторного начисления; устаревшее событие не откатывает новое состояние |
| Отмена/ошибка/истечение | Авторитетные состояния и правила переходов | UI читает серверный статус; неуспешная оплата не выдаёт доступ; истечение/возврат/отмена действуют по правилам платформы |

Согласовать транспорт (HTTPS), service identity/доступные scope, ограничения частоты, коды ошибок, таймауты, retries только для идемпотентных операций, версионирование, тестовый контур, refresh/revoke токенов, минимизацию PII и журналирование без токенов.

## Схема взаимодействия
Пользователь → существующий вход TRIOZ Business → подтверждённое связывание → авторизация основной платформы → сервер Business получает проверенный subject → server-to-server чтение статуса/возможностей → UI.

Пользователь выбирает разрешённый сценарий → сервер Business проверяет сессию/CSRF/связь и разрешённый тариф → сервер основной платформы создаёт checkout → провайдер → проверенный webhook в основной платформе → основная платформа идемпотентно учитывает оплату/подписку → Business читает авторитетный результат или принимает проверенное событие инвалидирования кэша → UI.

Предпочтительно существующая платёжная подсистема основной платформы принимает provider webhook. Не переносить его в Business ради удобства. Редирект на страницу результата показывает «проверяем оплату», а не выдаёт доступ. Если требуется оплата разовой услуги Business, необходимо отдельно решить владельца заказа, бухгалтерского учёта и отношений с платформой; подписка не возникает автоматически.

В Business допустима минимальная таблица подтверждённых связей аккаунтов в обеих схемах, но не независимая база подписок. Необязательный короткоживущий кэш статуса не источник истины. Политику stale/недоступности согласовать: не выдавать новые возможности при неизвестном статусе; не разрушать существующие обычные проекты из-за недоступности API. Никаких прямых обращений к production-БД платформы.

## Условный план реализации после получения API
Это предлагаемые файлы/маршруты Business, не найденные маршруты trioz.ru; окончательные имена и payload — после контракта.
1. `lib/platform-client.ts`: серверный адаптер реального API, auth, схемы ответа, таймауты и безопасные ошибки. Секреты без NEXT_PUBLIC.
2. `lib/platform-identity.ts`: проверка токенов/одноразовых кодов выбранного механизма; отдельные ключи/назначения от локальной сессии.
3. `app/api/platform/link/route.ts`, `app/api/platform/callback/route.ts`: начало/завершение связывания с state/PKCE и проверкой локальной сессии; защита unlink от CSRF. Callback не может полагаться только на совпадение email.
4. Обе `schema.*.prisma` и новые миграции обеих историй: минимальная account link с уникальным платформенным subject, без копии подписок; транзакционность смены связи.
5. `app/api/platform/subscription/route.ts`: защищённое чтение сервером авторитетного статуса/прав; отсутствие утечки чужого subject, безопасные ошибки/таймауты.
6. `app/api/payments/session/route.ts`: только если контракт и сценарий утверждены; сессия + CSRF, тариф/цена по доверенному API, idempotency; не произвольный провайдер.
7. Страница результата оплаты: серверная перепроверка, состояние ожидания, отмена и неуспех. Основная платформа продолжает подтверждать платёж и выдавать подписку.
8. `app/api/platform/events/route.ts` только если реальный API предусматривает такие события: проверка подписи raw body, replay, eventId, транзакция; invalidation/read-through вместо независимого начисления.
9. Тесты чужого subject, неподписанного/просроченного callback, replay, дубликатов и перестановки событий, подмены суммы/return URL, отмены/ошибки/возврата/истечения, недоступности платформы; sandbox-платежи и сверка с платформой. Выпуск отдельно согласовать.

## Входные данные и блокеры
- Доступ к исходникам основной платформы либо актуальная серверная API-спецификация и тестовый контур; владелец API и механизм межсервисной авторизации.
- Точный сценарий: разовая услуга Business, покупка тарифа платформы или продление; правила связи заявки, заказа и подписки.
- Действующий платёжный провайдер и его серверная документация: создание/проверка, подпись webhook, retries, идемпотентность, sandbox.
- Подтверждённые тарифы, цены, валюты, правила доступности и продления.
- Учёт платежей, чеки/налоги при применимости, возвраты, отмены, chargeback и аудит; юридические и платёжные реквизиты оператора/получателя, условия договора и требования к данным.
- Правила обработки/хранения данных и токенов, места обработки, полномочия пользователей и регламент поддержки.

До получения этих сведений подключение провайдера небезопасно. Платёжный код в данную доработку не включён.
