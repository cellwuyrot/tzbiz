# Выпуск обновления почты: только tzbiz

## Важные границы

Эта доработка подготовлена локально поверх cb7c056f1e076ad1d080eff9913b503d2140b9f9. Архив/patch **не опубликованы на GitHub и не установлены на вашем сервере**. Сначала внесите изменения в репозиторий и включите их в main; обычный git pull до этого ничего нового не установит.

Рабочая база уже PostgreSQL tzbiz_business, роль tzbiz_app, localhost:5432. SQLite переносить заново не нужно. Никакого DROP DATABASE, migrate reset, db push, db:setup или seed. Повторный seed может изменить администратора. Старая .env остаётся на сервере; не заменяйте её .env.example. Не изменяйте другие каталоги, роли, базы, PM2-процессы, Nginx. Не выполняйте pm2 update/restart all/stop all.

Деплой in-place требует короткого окна обслуживания: npm ci и замена .next могут повлиять на текущий процесс даже до перезапуска. Для нулевого простоя нужен отдельно согласованный release-directory deployment; эта инструкция не обещает zero downtime.

## 1. Опубликовать изменения в GitHub

На своей машине клонируйте репозиторий. Предпочтительный способ — применить приложенный patch, который содержит только изменения исходников/документов/тестов/новой миграции. Он рассчитан на указанный базовый коммит. Если GitHub уже изменился, не делайте reset --hard и не перезаписывайте новые изменения архивом: сначала объедините изменения и повторите проверки.

Пример для совпадающей основы (patch предварительно положите в текущий каталог):

```bash
git clone https://github.com/cellwuyrot/tzbiz.git
cd tzbiz
git rev-parse HEAD
git apply --check ../TRIOZ-mail-upgrade.patch
git apply ../TRIOZ-mail-upgrade.patch
git diff --check
git status --short
# Просмотрите изменения; никаких .env/БД/паролей в коммите.
git add app components lib prisma tests docs README.md .env.example
git commit -m "Add SMTP diagnostics and per-channel lead notification status"
git push origin main
```

Если main защищена — публикуйте отдельную ветку и объединяйте через PR. ZIP является альтернативным исходником для сравнения, не командой замены всего рабочего каталога сервера.

## 2. На сервере — проверить каталог и локальные правки

```bash
cd /var/www/tzbiz
pwd
git status --short
git remote get-url origin
pm2 status
```

Если есть локальные правки, сначала сохраните/согласуйте их. Не используйте автоматический reset --hard или stash pop после обновления: они могут потерять правки/вернуть старый код. Не выводите .env, pm2 env или полные process.env в чат.

## 3. Резервная копия только этого проекта

В текущем root-сеансе, до npm ci и миграции:

```bash
cd /var/www/tzbiz
umask 077
BACKUP="/root/tzbiz-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$BACKUP"
git rev-parse HEAD > "$BACKUP/commit.txt"
git diff --binary > "$BACKUP/local-changes.patch"
tar --exclude='./.git' --exclude='./node_modules' --exclude='./.next' \
    -czf "$BACKUP/tzbiz-files.tar.gz" .
runuser -u postgres -- pg_dump -p 5432 -d tzbiz_business -Fc \
    > "$BACKUP/tzbiz_business.dump"
test -s "$BACKUP/tzbiz_business.dump" && echo "Резервная копия создана"
```

Проверьте код завершения pg_dump и пригодность копии к восстановлению до продолжения. Архив файлов содержит .env/uploads и потому конфиденциален: не отправляйте его в чат, не коммитьте. pg_dump читает только указанную БД; ничего не удаляет и не мигрирует. Если PostgreSQL установлен на нестандартном socket/кластере, уточните существующий способ локального резервирования, не меняйте конфигурацию сервера ради команды.

## 4. Получить опубликованный код

```bash
cd /var/www/tzbiz
git pull --ff-only origin main
test -f prisma/migrations-postgresql/0005_mail_observability/migration.sql
```

Если pull отказал из-за локальных изменений либо миграция отсутствует — остановитесь. Не запускайте остальные шаги на другой версии.

Проверка целевой .env без пароля:

```bash
node -e '
const fs=require("fs"), dotenv=require("dotenv");
try {
  const u=new URL(dotenv.parse(fs.readFileSync(".env")).DATABASE_URL);
  if (!["postgres:","postgresql:"].includes(u.protocol) ||
      u.hostname!=="127.0.0.1" || !["","5432"].includes(u.port) ||
      u.username!=="tzbiz_app" || u.pathname!=="/tzbiz_business") throw Error();
  console.log("Целевая .env: PostgreSQL tzbiz_business / tzbiz_app");
} catch { console.error("Проверьте .env: продолжать нельзя"); process.exit(1); }
'
```

Ниже env -u DATABASE_URL убирает возможное SSH-переопределение только для команды; не удаляет .env. Если у приложения есть .env.local/.env.production или переменные в PM2 ecosystem, они должны указывать на ту же целевую базу. Не печатайте их секретные значения. PM2 --update-env само по себе не гарантирует удаление старых переменных окружения.

## 5. Миграция, генерация и проверки

Только после проверенной копии и согласованного окна обслуживания:

```bash
cd /var/www/tzbiz
npm ci && \
env -u DATABASE_URL NODE_ENV=production npm run db:deploy && \
env -u DATABASE_URL NODE_ENV=production npm run db:generate && \
npm run lint && \
npm run typecheck && \
npm test && \
env -u DATABASE_URL NODE_ENV=production npm run build
```

В истории уже 0001–0004; migrate deploy применит только недостающую 0005. Старые заявки и согласия сохраняются, статусы писем старых заявок — «Нет истории отправки», попыток 0. Клиентские проекты, пароли и роли не пересоздаются. Не продолжайте при любой ошибке. Не запускайте npm audit fix --force для быстрого обхода предупреждений.

## 6. Перезапустить исключительно tzbiz

После успешной сборки:

```bash
pm2 restart tzbiz --update-env
pm2 status
```

Проверьте online именно tzbiz и HTTP-ответы сайта. Не выполняйте глобальный restart/update. pm2 save сохраняет общий список всех процессов и для обычного restart не требуется; здесь намеренно не используется.

## 7. Проверить в браузере

1. Главная: кнопки заявки ведут в #contact, карточка выбирает услугу; ввод не теряется при переходе из модального окна.
2. /agreement и /privacy публичны; оба согласия обязательны.
3. Админка → Интеграции: видны sender, внутренний адрес, reply-to, порт, TLS и признаки заполнения параметров — без логина/пароля.
4. «Проверить SMTP без отправки письма». Успех проверяет соединение/авторизацию, но не разрешение sender и не inbox.
5. После отдельного согласования тестового адреса и отправки на info@trioz.ru: введите тестовый email, поставьте подтверждение и отправьте два диагностических письма. Проверьте оба ящика/спам и Reply-To. Это не создаёт заявку.
6. Создайте согласованную тестовую заявку, убедитесь в сохранении и отдельных статусах. Не отключайте рабочий SMTP на production ради проверки сбоя — сценарий уже проверен локально.
7. При FAILED исправьте SMTP, затем повторите нужный канал; при UNKNOWN/отсутствии истории сначала проверьте ящик, повтор может дать дубль. Для SMTP_ACCEPTED повтор отключён. Повтор не создаёт вторую заявку и не меняет согласия.
8. Проверьте вход администратора, клиента, видимость клиентских проектов и редактирование существующих услуг/проектов.

## Откат

Если проверка/сборка не прошла — не перезапускайте новый код. Старые модели не используют добавленные поля, поэтому 0005 не следует удалять автоматическим downgrade. Отдельно согласуйте восстановление предыдущего коммита и его node_modules/.next с сохранением новых данных. Не восстанавливайте dump поверх БД без оценки заявок, поступивших после копии. Копия и процедура восстановления нужны до начала выпуска.
